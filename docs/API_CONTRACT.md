# meYou — API Contract (client side codes against this; real servers are written separately)

If a phase needs a change, edit this file and record it in HANDOFF under "Contract changes". Never silently diverge.
All requests: `Authorization: Bearer <token>` (**except** `GET /api/v1/ping`, which is public, see D.3), JSON unless stated, UTF-8. All timestamps: UTC ISO 8601.

## SERVER 2.0 (stage 2C) — supersedes D.5, D.6, D.8, D.9, D.10 (mailbox part), D.13 and sections A, B, B2

The 2.0 server is deliberately small. **Kept:** `GET /ping` (public), `GET /me`, `POST /invites`, `POST /join` (public), `DELETE /devices/{id}`, the encrypted queue (`/e2e/queue`, `/e2e/ack`, `/e2e/stats`, `/e2e/ws`, below), `PUT/DELETE /push/token` (D.11), lockout and request log (D.12). **Removed (now `404`):** `/roots`, `/tree`, `/items/*`, `/changes`, `/uploads/*`, `/mailbox`, `/mailbox/ws`. Nothing about photos, memories, events or chat is stored on the server; every phone-to-phone message is an opaque encrypted blob in the queue.

- `/ping` -> `{name, version:"2.0.0", features}` with `features` = `["e2e"]`, plus `"push"` when the Firebase key loaded. `media`, `upload`, `mailbox` are no longer announced. The app requires `e2e`.
- Limits (env): `MAILBOX_RATE_LIMIT_MAX` 1200 requests/min/IP on `/e2e/*` (name kept for old `.env` files), `E2E_MAX_BLOB_KB` 1024 (decoded blob; request body up to 4/3 of it + 1 KB), `E2E_TTL_DAYS` 30, `E2E_MAX_QUEUE_MB` 256 (`507 queue_full`). Settings `SCAN_*`, `UPLOAD_*`, `MEDIA_*`, `MAILBOX_RETENTION_DAYS`, `MAILBOX_MAX_MESSAGES` are gone (ignored if still set).
- Database: schema version stays 7. Tables `items`, `changes`, `uploads`, `mailbox` are legacy and unused; the CLI command `purge-legacy` (opt-in, irreversible) empties them.
- Push: only generic `e2e` pushes (data only, or visible with `wake:true`); the per-type texts of D.11 are no longer sent by the server and their code is deleted (stage 2E cleanup). `PUSH_PERIOD_DETAIL` no longer exists (ignored if still in a `.env`). Because the server cannot see types, a visible push is skipped only when the device switched ALL four `notify` keys off; `data.type` is `e2e` (or `test` for `push-test`).

## A. File server (`/api/v1`)
- `GET /ping` → `{ name, version, features: string[], certFingerprint? }`
- `GET /roots` → `[{ id, name }]` (library roots configured on the server)
- `GET /tree?root=&path=&cursor=&limit=` → `{ items: Item[], nextCursor? }`
  `Item = { id, name, type: "dir"|"image"|"video"|"file"|"text", size, mtime, md5?, mime?, width?, height?, duration? }`
- `GET /items/{id}/thumb?size=256` → image/jpeg
- `GET /items/{id}/preview` → image/jpeg (≈1600 px) or video poster
- `GET /items/{id}/file` → original, **supports HTTP Range**
- `GET /changes?since=<cursor>` → `{ changes: [{ id, op: "add"|"update"|"delete", item? }], cursor }`
- Resumable upload: `POST /uploads {name, size, rootId, path, md5?}` → `{ uploadId, offset }`; `PATCH /uploads/{uploadId}` with header `Upload-Offset` and a binary chunk → `{ offset }`; `POST /uploads/{uploadId}/complete` → `Item`
- ~~Server-side sync~~ (superseded by B2, do not implement): `POST /sync/jobs { mapping, direction, conflictPolicy, deletionPolicy, dryRun }` → `{ jobId }`; `GET /sync/jobs/{jobId}` → `{ state, progress, log[] }`; `POST /sync/jobs/{jobId}/cancel`

## B. Partner mailbox = ntfy (replaces the old custom relay; Phase 7, verified against docs.ntfy.sh)
No server of ours. Uses the documented ntfy HTTP API of a self-hosted server or ntfy.sh (existing software, Apache-2.0/GPL-2.0).
- Publish (JSON publish, so emoji/Persian titles need no header encoding): `POST {ntfyUrl}/` with `{ "topic", "title", "message" }`; the reply is the stored message `{ id, time, event, topic, ... }`. `message` is the JSON body below (ntfy caps it at 4096 characters; the app stays under 4000 and never truncates). `title` is a readable summary (`meYou 😊`) so the ntfy Android app shows something sensible.
- Subscribe: `WS {ntfyUrl}/{topic}/ws?since=<unix seconds>` while the app is open; frames are JSON `{ id, time, event: "open"|"keepalive"|"message", message }`. On every (re)connect the app passes the `time` of the last message it handled (or the pairing time minus 60 s), so a reconnect replays what was missed; messages are deduplicated by ntfy id. `GET {ntfyUrl}/{topic}/json?poll=1&since=latest` is used only as the connection test.
- Pairing payload (QR/code): `{ "v":1, "ntfyUrl":"https://…", "topic":"<32-64 chars A-Za-z0-9_->", "token"?:"<access token>" }`. The topic (24 random bytes = 32 chars) is the shared secret. For a private server `Authorization: Bearer <token>` is sent on publish, poll and the WebSocket upgrade (React Native's non-standard `new WebSocket(url, undefined, { headers })`). Topic and token live in SecureStore.
- Message body (JSON): `{ "t":"mood"|"event"|"profile"|"unpair", "from":"<deviceId>", "ts":"<UTC ISO>", ... }`
  - `mood: { emoji, text?(≤200), intensity:1-5 }`
  - `event: { id, title, date, repeat?:"yearly", cal?:"jalali"|"gregorian", deleted?:true }` — same `id` = create or replace; `deleted` removes it (then only `id` matters). `date` is a UTC ISO date; `cal` is the calendar a yearly repeat follows (default: the receiver's chosen calendar). Tags and the Library attachment stay local.
  - `profile: { name?, avatarB64?(64 px JPEG), avatarPhoto?(R10c: server path `Shared/avatar-<deviceId>/<file>.jpg` of a 512 px JPEG, D.13), birthday?(UTC ISO date), hello?:true }` — `hello` is sent by the phone that just joined; the other phone answers with its own profile (without `hello`).
  - `unpair: {}` — the sender removed the pairing; the receiver drops the topic too.
- Unpair rotates the secret: both phones delete the topic; the next pairing generates a new random topic, the old one is never reused.
- A phone ignores messages whose `from` is its own device id (it receives its own publishes on the topic).

## B2. Server-side sync = rclone (Phase 6)
No custom endpoint. rclone's built-in remote control API (`rclone rcd`, started with `--rc-addr`, `--rc-user/--rc-pass`) is used: start `sync/copy` with `_async: true`, poll `job/status`, read the log. The old `POST /sync/jobs` in section A is not used any more. Verify exact rc calls against rclone.org/rc at the start of Phase 6.

## C. Contract additions (Phase 4; all backward compatible)
Client and server must follow these; they clarify section A and add the QR payload.
1. **Auth for media**: every request, including `GET /items/{id}/thumb|preview|file`, carries `Authorization: Bearer <token>` as a header. The token is never put in a URL. The app passes the header to image loading, downloads and the video player (which sends it on every Range request).
2. **Resuming uploads**: a repeated `POST /uploads` with the same `rootId, path, name, size, md5` for an unfinished upload returns the existing `{ uploadId, offset }` (current offset). `PATCH /uploads/{id}` with an `Upload-Offset` that differs from the server's offset answers `409 { offset }` (the client re-syncs to that offset). The client sends 1 MiB chunks with `Content-Type: application/offset+octet-stream`. `POST .../complete` fails with `400` if the file is incomplete and `422` if the given `md5` does not match. The server creates missing folders of `path`.
3. **`/changes` items** MAY include `root` and `path` (root id and path of the item including its name) so the client can address it. Without them the client cannot resolve folders for that change.
4. **`/ping.certFingerprint`** (https only) is the SHA-256 of the server's leaf certificate as hex, optionally with `:` separators. The app shows it for confirmation (real pinning: Phase 11).
5. **No delete operation** exists in section A; the app never deletes server files.
6. **QR payload** (shown by the server or its installer), one of:
   - JSON: `{"url":"https://host:8443","token":"...","name":"Home","fp":"AA:BB:..."}` (`name`, `fp` optional)
   - Link: `meyou://server?url=<urlencoded>&token=<urlencoded>&name=<urlencoded>&fp=<urlencoded>`

## D. Own server: household, auth, bootstrap, media reads, uploads, partner mailbox (server track; S1, S3, S5, S7, S9 built; S11 hardening; S11 push opt-out)
The server lives in `server/meyou-server/`. Sections A and C stay valid; S3 implemented their read side (D.8), S5 implements uploads. One household per server, at most 2 devices. Status per item: **[S1]** implemented, **[S9]** planned (not available yet; the app must read `features` from `/ping`).

### D.1 Bootstrap (server CLI, not HTTP) [S1]
`meyou-server init` (in Docker: `docker compose exec meyou-server meyou-server init`) creates the household, the **owner** device and its token, and the folders `library/Photos` and `library/Videos`. It prints, once:
- a link `meyou://server?url=<urlencoded https://DOMAIN>&token=<urlencoded>&name=<urlencoded server name>`,
- an ASCII QR code of that link,
- the JSON payload `{"url","token","name"}` (same payload as C.6; `fp` is not used).

The token is 32 random bytes (base64url, 43 chars). The server stores only its SHA-256 hash, so it cannot be shown again. A second `init` prints `Already initialized` and changes nothing.

### D.2 Authentication [S1]
`Authorization: Bearer <token>` on every request except D.3. Tokens are never sent in URLs (also not for WebSocket, see D.6). A missing, malformed, wrong or revoked token gives `401 { "error": "unauthorized" }` with `WWW-Authenticate: Bearer`; unknown paths also give 401 without a token (routes are not revealed).

### D.3 `GET /api/v1/ping` (public) [S1]
`→ { "name": string, "version": string, "features": string[] }` and nothing else. `features` may contain `media`, `mailbox`, `push`; S1 returned `[]`, since S3 `["media"]` (browse, thumbnails, originals, changes) and **since S5 `["media","upload"]`** (`upload` = the resumable upload routes of D.9). **since S7 `["media","upload","mailbox"]`** (`mailbox` = the partner routes of D.10). `features` may contain `media`, `upload`, `mailbox`, `push`. **Since S9 `push` is appended (`["media","upload","mailbox","push"]`) only when the Firebase credentials loaded**; without a usable key file the list stays `["media","upload","mailbox"]`. The app switches a module on only when the server announces it. (`certFingerprint` from section A is not provided by this server: Caddy terminates TLS.)

### D.4 `GET /api/v1/me` [S1]
`→ { "deviceId": string, "role": "owner"|"member", "household": { "partner": { "deviceId": string, "name": string } | null }, "features": string[] }`. `features` equals the one in `/ping`. `partner` is the other non-revoked device of the household, else `null`.

### D.5 `GET /api/v1/roots` [S1]
`→ [{ "id": string, "name": string }]`, sorted by name. Each real directory directly under `$DATA_DIR/library/` is a root; the id equals the name. Files, dot-entries and symlinks are ignored. (This is section A `/roots`, unchanged in shape.)

### D.6 Planned in later phases (not available in S1)
- **[S7]** invites, join, devices, mailbox and its WebSocket are built: see **D.10**.
- **[S9]** push token routes are built: see **D.11**.

### D.7 Errors and limits [S1]
Error bodies are keys, never user-facing text: `{ "error": "<key>" }` with keys `unauthorized` (401), `rate_limited` (429, plus `Retry-After` header and `retryAfter` seconds), since S11 `locked_out` (429, plus `Retry-After` header and `retryAfter` seconds, see D.12), `not_found` (404), `bad_request` (400), `payload_too_large` (413), `internal_error` (500), and since S3 `unsupported_media` (415, a thumbnail/preview cannot be made for this file) and `range_not_satisfiable` (416). and since S7 `forbidden` (403), `invalid_code` (400), `household_full` (409), `no_partner` (409), `last_device` (409), and since S5 `offset_mismatch` (409, with `offset`), `upload_incomplete` (400, with `offset`), `md5_mismatch` (422), `insufficient_storage` (507). Request bodies are limited to 64 KiB (the upload `PATCH` raises its own limit, D.9). Rate limits per client IP: 600 requests/minute overall, 30/minute on public routes, and (S3) 6000/minute on `thumb`, `preview` and `file` because a library grid asks for many and (S5) 6000/minute on `/uploads` routes (`RATE_LIMIT_MAX`, `PUBLIC_RATE_LIMIT_MAX`, `MEDIA_RATE_LIMIT_MAX`, `UPLOAD_RATE_LIMIT_MAX`). No CORS headers are sent.

### D.8 Media read API [S3]
Implements the read side of sections A and C. All routes need the Bearer token (the token is never in a URL). The server indexes `$DATA_DIR/library` into SQLite at start and again every `SCAN_INTERVAL_SECONDS` (default 300; 0 = start only); files copied in by hand appear after the next scan. Dot-files/dot-folders, symlinks and names that are not valid UTF-8 are ignored; the server never follows symlinks.
- **Item ids** are stable: `base64url(sha256(root + NUL + path))` cut to 22 chars, so the same file keeps its id across restarts and rescans. A rename or move is a `delete` of the old id plus an `add` of the new one.
- **`Item`**: as in section A. `type` is `dir|image|video|file|text` (by extension, with a magic-byte check when there is no known extension). `mtime` is UTC ISO 8601. `width`/`height` (EXIF rotation applied) for images, `width`/`height`/`duration` (seconds) for videos when readable. `md5` is **not** provided (optional in the contract); uploads (S5) and backup (S6) compare name + size.
- **`GET /tree?root=&path=&cursor=&limit=`** → `{ items, nextCursor? }`. `root` is required (a root id from `/roots`), `path` is the folder inside it (empty or `/` = the root). Folders first, then by name (case-insensitive), `limit` 1..500 (default 100, larger values are clamped). `nextCursor` is opaque; absent on the last page. Errors: `400` for a missing/invalid `root`, a `path` with `..`, `.`, empty segments, `\` or NUL, a bad `cursor` or `limit`; `404` for an unknown root, a missing folder, or a path that is a file.
- **`GET /items/{id}/thumb?size=256`** → `image/jpeg`, longest side = `size`, never enlarged, EXIF rotation applied. `size` is rounded up to one of 64, 128, 256, 384, 512, 768, 1024 (default 256; bigger is clamped to 1024; non-numeric or 0 is `400`). **`GET /items/{id}/preview`** → `image/jpeg`, longest side 1600 (never enlarged). Videos return a frame (about 1 s in). Both carry `ETag` and answer `304` to `If-None-Match`; `Cache-Control: private, no-cache`. `415 unsupported_media` for files that are not images/videos or cannot be decoded (for example HEIC encoded with HEVC), `404` for a folder or an unknown id. Results are cached in `$DATA_DIR/cache` and rebuilt when the file changes.
- **`GET /items/{id}/file`** → the original. `Accept-Ranges: bytes`, `Content-Length`, `ETag`, `Last-Modified`, `Content-Type` from the item, `Content-Disposition: inline` (UTF-8 file name). One byte range is supported: `bytes=a-b`, `bytes=a-` and `bytes=-n` answer `206` with `Content-Range`; an end past the file is clamped; a malformed or unsatisfiable range answers `416` with `Content-Range: bytes */size`; a multi-range request or another unit is ignored (full `200`). `If-Range` (ETag or date) and `If-None-Match` (`304`) are honoured; `HEAD` works.
- **`GET /changes?since=<cursor>&limit=`** → `{ changes, cursor }`. `cursor` is an opaque string (a number today); no `since` means from the start. Every change has `id`, `op` (`add|update|delete`), `root` and `path` (C.3); `item` is present for `add`/`update` with the item's current state. Page with `limit` (1..1000, default 500) and repeat with the returned `cursor` until `changes` is empty. Folders are reported as `add`/`delete` only. The log keeps the last 200,000 entries; a client that was offline longer than that should list the tree again.

### D.9 Resumable upload [S5]
Implements section A "Resumable upload" and C.2. All routes need the Bearer token. **There is no delete or overwrite operation.**
- **`POST /uploads`** body `{ name, size, rootId, path, md5?, mtime? }` (JSON). `rootId` must be an existing root (`404` otherwise). `path` is the **destination folder** inside the root (`""` or `"/"` = the root itself; missing folders are created when the upload completes). `name` is one file name. `md5` (32 hex chars, optional) is checked on complete. `mtime` (optional; milliseconds since the epoch or an ISO 8601 string, not more than a day in the future, else `400`) becomes the file's modification time, so a backed-up photo keeps its date and the app can match it with the phone's copy. → `200 { uploadId, offset }`. Invalid input gives `400`: `name`/`path`/`rootId` segments that are empty, `.`, `..`, start with `.` (the indexer ignores dot-files), contain `/`, `\`, NUL or control characters, are longer than 255 bytes, or a folder on the way that is a symlink or a file; `size` that is not a whole number ≥ 0. `413` when `size` is above `UPLOAD_MAX_FILE_MB`; `507 insufficient_storage` when `size` + what other open sessions still expect + `UPLOAD_MIN_FREE_MB` does not fit on the disk.
- **Resume (idempotent):** the same `{rootId, path, name, size, md5}` from the same device for an unfinished upload returns the **existing** `{ uploadId, offset }` with the bytes the server really has (the temp file size is the offset, so bytes of a dropped chunk that did arrive are kept). If the same request (with `md5`) arrives within 10 minutes after the upload finished and the file is still there, it returns `{ uploadId, offset: size }` and `complete` answers with the item again. Without `md5` a finished upload is never reused (two different files with the same name and size must both be kept).
- **`PATCH /uploads/{uploadId}`** headers `Upload-Offset: <n>` and `Content-Type: application/offset+octet-stream` (also `application/octet-stream`), body = one chunk (the app sends 1 MiB; the server accepts up to `UPLOAD_MAX_CHUNK_MB`, default 8). → `200 { offset }` (the new offset). If `Upload-Offset` differs from the server's offset: `409 { error: "offset_mismatch", offset }` and nothing is written (the client continues from that offset). Missing or malformed header/content type: `400`; chunk above the limit: `413`; chunk that goes past `size`: `400` (nothing kept); not enough free disk space: `507` (nothing kept). Requests for one session are handled one at a time. Unknown, finished or malformed id: `404`.
- **`POST /uploads/{uploadId}/complete`** → `200 Item` (as in D.8, already in the index and in `/changes`, so it is listed at once). `400 { error: "upload_incomplete", offset }` while bytes are missing; `422 { error: "md5_mismatch" }` when the md5 given at create differs (the session and its temp file are then deleted, so the same request starts again at offset 0). Calling it again for a finished session returns the same item.
- **Placement:** the file is moved atomically into `library/<rootId>/<path>/<name>` (hard link, fails if the name exists). **A name that exists (file or folder) is never overwritten:** the server uses `name (1).ext`, `name (2).ext`, … (suffix before the last dot) and returns the final name in the `Item`. Temp files live in `$DATA_DIR/uploads`, outside the library; unfinished sessions idle longer than `UPLOAD_SESSION_TTL_HOURS` (default 48) and unknown temp files older than an hour are removed (at start and hourly). Without `mtime` the modification time is the time of the upload.

### D.10 Partner: invites, join, devices, mailbox [S7]
One household, **at most 2 active devices**. The device created by `init` is the `owner`; a device that joined is a `member`. A revoked device keeps its row but its token stops working. Error bodies are keys (D.7).

- **`POST /invites`** (owner; a member gets `403 forbidden`) → `200 { code, expiresAt, link }`. `code` = 24 characters from `ABCDEFGHJKMNPQRSTUVWXYZ23456789` (no look-alikes), single use, valid 30 minutes, stored only as a SHA-256 hash. `link` = `meyou://join?url=<urlencoded base URL>&code=<code>` (base URL = `PUBLIC_URL`, else the request's). A new invite replaces every older unused one. `409 household_full` when 2 devices are active.
- **`POST /join`** body `{ code, deviceName }` (**public**, rate limited per IP: `JOIN_RATE_LIMIT_MAX`, default 10/min) → `200 { deviceId, token }`; the token (32 random bytes, base64url) is shown only here. `deviceName` is 1..64 characters without control characters (`400 bad_request`; checked before the code is used). A code that is unknown, used, expired or malformed answers the same `400 invalid_code`. `409 household_full` when 2 devices are already active (also for a code created earlier). Typed codes may use lower case, spaces and dashes.
- **`DELETE /devices/{id}`** (the owner may revoke any device of the household, a member only itself; `403 forbidden` otherwise) → `200 { revoked: true }`. The token stops working at once (`401`), its open WebSockets are closed with code `4401`, its push token is cleared and the messages still waiting **for** it are deleted (messages it sent stay for the partner, so an `unpair` message sent just before leaving still arrives). An unknown id, another household's id or an already revoked device is `404 not_found`. **The last active device cannot remove itself** (`409 last_device`: nobody could sign in again). When the owner leaves, the remaining device becomes the `owner` (it can invite a new partner). This is how "unpair" works; the household then has room for a new partner.
- **`GET /me`** (D.4) now shows the partner as soon as one joined: `household.partner = { deviceId, name }`; `null` after a revoke.
- **`POST /mailbox`** body = the partner message JSON of section B (`t`: `mood|event|profile|unpair`, since R1a also `diary|period`, later `story|story-seen`, `chat-seen` (`{ t: "chat-seen", id, silent: true }` = "I read your texts up to `id`", data-only push, needs server 1.2.0+ files of 2026-10-24) and `chat` (a plain direct text: `{ t: "chat", id, text }`, text only, ≤ 2000 characters; the push is visible with the generic text "New message from your partner" / «پیام جدیدی از همراهت رسید» and has no `notify` switch), plus `from` (1..64 chars) and `ts` (ISO 8601); the other fields are not checked by the server and are stored unchanged), ≤ **32 KB** (`413 payload_too_large`). → `200 { seq, time }`. The message goes to **the other active device only** (the sender never gets it back); `409 no_partner` when there is none. Missing/invalid `t`, `from`, `ts` or a non-object body is `400 bad_request`.
- **`GET /mailbox?since=<seq>&limit=<n>`** → `{ messages: [{ seq, time, body }], cursor }`: the messages addressed to the caller with `seq > since` (default 0), oldest first, `limit` 1..200 (default 100, larger is clamped). `body` is the stored message object. `cursor` = the last returned `seq` (or `since` when there is none), as a string; repeat with it until `messages` is empty. `seq` only grows (never reused, gaps are normal); the client de-duplicates by `seq`. `400` for a malformed `since`/`limit`.
- **`GET /mailbox/ws?since=<seq>`** WebSocket, token in the `Authorization: Bearer` header of the upgrade request (never in the URL: a wrong, missing, URL-only or revoked token is refused with `401`, no socket). The server first sends every stored message with `seq > since` (default 0) as `{ "type": "message", "seq", "time", "body" }`, then `{ "type": "ready", "cursor": "<seq>" }`, then each new message for this device as it arrives (no gaps, no doubles). Frames from the phone are ignored (send with `POST /mailbox`, at most 1 KB is accepted). The server pings every 30 s and drops a socket that does not answer; a device may hold 4 sockets (the oldest is closed with code `4000` when a 5th opens). Close codes: `4400` bad `since`, `4401` revoked, `4000` replaced. The app reconnects with `since=<last seq it saw>`.
- **Retention (Q3):** a message is deleted after `MAILBOX_RETENTION_DAYS` (30) or when the household has more than `MAILBOX_MAX_MESSAGES` (1000), oldest first (checked on every post and hourly).
- **Limits:** `MAILBOX_RATE_LIMIT_MAX` (300/min per IP) on `/mailbox` routes; `/invites` and `/devices` 20/min.

### D.11 Push (FCM) [S9]
The server wakes the partner's phone through Google FCM (HTTP v1, `firebase-admin`). Push is on only when `FCM_SERVICE_ACCOUNT_FILE` points to a usable Firebase service-account key; then `/ping` and `/me` announce `push` (D.3). Tokens can be registered either way (a server without a key just stores them).

- **`PUT /push/token`** body `{ fcmToken, lang, notify? }` → `200 { registered: true }`. `fcmToken` = 32..4096 printable ASCII characters without spaces; `lang` = the app's UI language (`fa`, `en`, `fa-IR`, `fa_IR`, ... 2..16 characters; `_` is stored as `-`). `400 bad_request` for anything else. One token belongs to one device: registering a token that another device row holds clears it there. Call it after pairing and again whenever FCM refreshes the token or the app language changes. **`notify` (since S11, optional):** `{ mood?: boolean, event?: boolean, diary?: boolean, period?: boolean }` (`diary` and `period` since R1a) = which system notifications this device wants. `false` makes the server **skip the FCM send** for that type (the message is still stored in the mailbox and reaches the app by socket/replay as always); `profile` and `unpair` are silent data-only pushes and are never switched off. A key that is left out, or no `notify` at all (an app from before S11), keeps the stored choice; the default for a new device is on for both. Anything else (`notify` not an object, a non-boolean value) is `400 bad_request` and nothing is stored. The choice survives `DELETE /push/token` (it is a preference, not a token) and is kept per device row; `meyou-server push-test` ignores it. The app sends the full `{ mood, event }` on every registration.
- **`DELETE /push/token`** → `200 { removed: true }` (idempotent). Revoking a device (D.10) also clears its token.
- **What is sent:** for every message stored by `POST /mailbox`, one FCM message to the **recipient's** token (never the sender, nothing when the recipient has no token). The server does not skip it when a WebSocket is open.
  - `mood` and `event` (Q1/Q2): notification + data. `title` = `meYou`; `body` is generic and localized, never contains message content: `mood` = "New status from your partner" / «وضعیت جدیدی از همراهت رسید», `event` = "New event from your partner" / «رویداد جدیدی از همراهت رسید» (Persian when `lang` starts with `fa`, English otherwise). Android: priority `high`, TTL 24 h, channel id **`meyou-partner-v2`** since R1a (before: `meyou-partner`; the app must create this channel).
  - `profile` and `unpair`: **data only** (no `notification`), priority `normal`, TTL 24 h.
  - **R1a, channel and sound:** the channel id is now **`meyou-partner-v2`** (the old `meyou-partner` has importance default and Android cannot change an existing channel, so the app creates a new one with importance high and sound in R1b). Every visible push also carries `android.notification.sound = default` and `priority = high`. A phone that does not have the v2 channel yet gets FCM's own fallback channel (sound, no pop-up) until the new app is installed.
  - **R1a, `diary` and `period`:** visible like `mood`/`event`, generic text only: `diary` = "New memory from your partner" / «خاطره‌ی جدیدی از همراهت رسید», `period` = "New update from your partner" / «خبر تازه‌ای از همراهت رسید». With `PUSH_PERIOD_DETAIL=true` (default off; the text then passes through Google) the `period` text names the update: "Your partner’s period started" / "Your partner is in pain" / "Your partner is feeling better" (and the Persian equivalents).
  - **R1a, markers the server reads in a message (never the content):** a push is **data only** (type kept, nothing shown, priority `normal`) when the message has `silent: true`, `cleared: true` (mood cleared) or `deleted: true` (a deleted event, memory, ...). A `period` message is visible only when `kind` is one of `started`, `pain`, `better`; any other or missing `kind` is data only. A data-only push is never switched off by `notify`; a visible one is skipped when the recipient's switch for that type is off.
  - `data` (all values strings) is always `{ type: "mood"|"event"|"profile"|"unpair"|"diary"|"period", seq: "<mailbox seq>" }`. The content is fetched from the mailbox (`GET /mailbox?since=`), not from the push. `meyou-server push-test` sends `type: "test"` with `seq: "0"` and a notification (the app should just show it).
- **Failures never fail the write.** The send runs in the background. An FCM answer `UNREGISTERED`, `INVALID_REGISTRATION_TOKEN` or `INVALID_ARGUMENT` deletes the stored token (only if it is still the same token). Temporary errors (unavailable, internal, rate exceeded, network, failed OAuth fetch) are retried twice, after 2 s and 10 s; then the push is dropped (the message is still in the mailbox). Other errors (e.g. wrong project) are logged once with their code and not retried.
- **Logs** carry only device id, message type and the error code: never a token, key text or message content.
- **Limits:** `PUSH_RATE_LIMIT_MAX` (60/min per IP) on the two routes.
- **CLI:** `meyou-server push-test [--check]` (also `sudo ./setup.sh push-test`): `--check` validates the key and prints the Firebase project id; without it a test notification goes to every phone that registered a token.

### D.12 Hardening: lockout, request log, admin CLI [S11, part 1]
- **Lockout.** An IP address that presents many *different* unknown credentials is refused for a while: unknown/revoked bearer tokens on any non-public route, and wrong invite codes on `POST /join`. Defaults: 10 distinct bad values within 10 minutes lock the address for 15 minutes (`AUTH_FAIL_MAX`, `AUTH_FAIL_WINDOW_MINUTES`, `AUTH_LOCKOUT_MINUTES`; `AUTH_FAIL_MAX=0` = off). The same wrong value repeated counts once (a revoked phone that keeps retrying never locks its Wi-Fi). While locked, every non-public route and `POST /join` answers `429 { "error": "locked_out", "retryAfter": <seconds> }` with a `Retry-After` header, **even with a valid token**; `GET /ping` stays public and unaffected. A request with a good token clears the address's earlier mistakes. State is in memory (a restart clears it). Clients treat it like `rate_limited`: wait `retryAfter`, do not drop the saved server or token.
- **Request log.** One line per answered request: method, route *pattern* (`/api/v1/items/:id/file`), status, milliseconds, IP, device id. Never the URL, query, header, token, file name or message text. `/ping` with 200 is debug level.
- **Admin CLI** (on the VPS, not HTTP): `meyou-server devices`, `rotate-token [<deviceId>|owner]` (new token + link/QR/JSON as C.6; the old token is invalid at once), `revoke <deviceId>` (same rules as `DELETE /devices/{id}`: last device refused, owner leaving hands ownership over, waiting messages dropped), `backup-db <file>` (SQLite `VACUUM INTO`, mode 600, never overwrites). A running server closes the WebSocket of a re-keyed/revoked device (code 4401) within 30 seconds.
- No change to any route shape, no new route, no DB migration.

### D.13 Protocol v2 for the refinement phases [R1a]
Server version 1.1.0, schema 6 (migration 6 adds `devices.notify_diary`, `devices.notify_period`, default 1, idempotent). No new route. Changes are in D.10 (`diary`, `period` message types) and D.11 (channel `meyou-partner-v2`, sound, `notify.diary`/`notify.period`, the `silent`/`cleared`/`deleted` markers, `period` kinds, `PUSH_PERIOD_DETAIL`). Attachments (event photo, memory media) do not travel in the mailbox (32 KB): the sender uploads them with D.9 into a library folder `Shared/<id>/` and the message carries the path; the partner reads them with D.8. An old app keeps working: it ignores the new types and the new channel id falls back to FCM's own channel.

**Client side of D.13 [R1b]** (app 1.1.x): the app creates channel `meyou-partner-v2` (importance HIGH, sound default), deletes `meyou-partner` and `partner`, and also shows its own local notifications on it. `app.json` `defaultChannel` = `meyou-partner-v2`. `PUT /push/token` now always sends `notify: { mood, event, diary, period }`. Message fields the app reads (anything else is dropped, an unknown `t` is ignored): `event` + `icon` (id, ≤ 32), `note` (≤ 1000), `photo` (server path `Shared/...`, ≤ 300, no `..`), `silent: true`; `profile` + `togetherSince` (ISO); `mood` + `cleared: true` (no emoji/intensity); `diary` `{ id, deleted? | title?, body?, category?, mood?, date?, mediaCount? }`; `period` `{ kind: started|pain|better, date?, cycleDays? }` (Q7: `cycleDays` = the sender's own cycle length, an integer 15–60, or `0` = none; sent with every `period` message, anything else is dropped; the server stores it unchanged, no server change). R1b only recognises `mood cleared`, `diary` and `period`; R3, R8a and R5b apply them.


**Client side of D.13 [R8a, R8b]**: `diary` is sent and applied. Fields: `id`; `title` (≤ 200), `body` (≤ 3000), `category` (built-in id, `none`, or the NAME of a custom category), `mood` (emoji), `date` (the memory's creation time, ISO), `media` (up to 99 photo/video paths under `Shared/<id>/`, uploaded with D.9; read with D.8), and `mediaCount` (legacy fallback for R8a clients); `silent: true` for a media-only change; `deleted: true` removes the receiver's copy. Same `id` = replace (older `ts` is ignored). The receiver never sends a received memory back. Removed shared files stay on the server because D.9 has no delete operation.

**Client side of D.13 [replies]** (app only, no server change): a reply under a memory is a `diary` message with `replyTo` = the memory's `id`, `id` = the reply's own id (`rp…`, ≤ 64), `text` (1..1000) and optional `date`; `deleted: true` (with `replyTo`) removes that reply. Both partners may reply; each phone stores replies in `diary_replies` (migration 12) and removes them with their memory. The receiver keeps a reply only for a memory it has, ignores a replayed reply id, and a delete message removes only the sender's own reply. An older app ignores these messages (no title, unknown id). The closed-app push still says the generic "New memory from your partner" text; the in-app notification says "New reply:" + the first 80 characters.

**Client side of D.13 [R2]**: the app now fills `event` `icon` (always sent, default `heart`; a message that carries `icon` replaces icon, note and photo on the receiver, one without leaves them), `note` (the event description) and `photo` (`Shared/<eventId>/<name>`, uploaded with D.9 using the pairing token before the message is sent; the partner reads it with D.8 `tree` + `preview`/`thumb`). `profile` carries `togetherSince` whenever it changes; a profile without it never clears the receiver's date. Shared files are never deleted (no delete route), also not when the event is deleted.

**Client side of D.13 [R10c]**: `profile` may carry `avatarPhoto` (≤ 300, `Shared/...` without `..`, anything else is dropped): the server path of a 512 px JPEG of the profile photo, uploaded with D.9 to `Shared/avatar-<deviceId>/avatar-<stamp>.jpg` before the message is sent. `avatarB64` (64 px) still travels in every profile message; the partner shows the tiny photo first and the sharper one once D.8 `tree` + `preview` finds it. A replaced photo gets a new file name; old files stay (no delete route). No server change.

## Encrypted queue (sharing track, stage 2; feature `e2e`)

Opaque blobs between the two phones. The phones encrypt (XChaCha20-Poly1305); the server has no key and never reads a blob. It knows sender, recipient, time and byte size. All routes need the Bearer token and are under `/api/v1`.

- `POST /e2e/queue` `{"id":"<1..64 of A-Za-z0-9_->","blob":"<base64url>","wake":<boolean, optional>}` -> `{seq,time}`. `wake:true` (stage 3) asks for a generic visible push; `wake` of another type -> `400 bad_request`. Same `id` from the same phone again -> the first row, `duplicate:true`. Errors: `400 bad_request`, `409 no_partner`, `413 payload_too_large` (`E2E_MAX_BLOB_KB`), `507 queue_full` (`E2E_MAX_QUEUE_MB` per recipient).
- `GET /e2e/queue?since=<seq>&limit=<1..50>` -> `{messages:[{seq,time,id,blob}],cursor,more}`. At most 4 MiB per answer (the first blob is always sent). Reading deletes nothing.
- `POST /e2e/ack` `{"seqs":[1..200 numbers]}` -> `{deleted}`. Deletes the caller's own blobs; unknown numbers are ignored; repeating is harmless. This is the only way (besides TTL) a blob leaves the queue.
- `GET /e2e/stats` -> `{count,bytes}` waiting for the caller.
- `GET /e2e/ws?since=<seq>` WebSocket: replay of what waits, then live frames `{type:"message",seq,time,body:{id,blob}}`, then `{type:"ready",cursor}` after the replay, then `{type:"presence",online}`: whether the other phone has a socket open right now (sent once after `ready`, and again whenever it changes; a phone that lost its last socket is announced offline only after a 15 s grace, so a quick reconnect does not flicker). No polling: presence is a by-product of the open socket. Apps ignore frame types they do not know. Close codes: 4400 bad `since`, 4401 revoked or re-keyed. The phone ACKs over HTTP.
- TTL: `E2E_TTL_DAYS` (30). Expired blobs are never delivered, and are deleted on the next post to that phone and hourly. Revoking a device deletes what waits for it.
- Push: FCM `{type:"e2e", seq}`. Data only by default; with `wake:true` it also carries the generic text "New update from your partner" (fa/en by the phone's language). No message type, no content. It is skipped when the recipient switched all four notification types off. Logs never contain a blob or an id.

### Blob format and what travels in it (stage 3, app side: `src/e2e/envelope.ts`, `src/e2e/transport.ts`)
- `blob = 0x01 | nonce(24 random bytes) | XChaCha20-Poly1305(padded plaintext)`; key = the sender's direction key; associated data `meyou-e2e1:q`.
- plaintext = JSON `{"v":1,"id":"<16 chars>","m":<the same PartnerMessage JSON as section B>}`, padded with `0x80` + zeros to a multiple of 256 bytes (the server sees size buckets only). `id` is also the POST `id`.
- Sender: with confirmed keys EVERY partner message (mood, event, diary, period, story, chat, like, comment, profile, unpair, seen marks) goes here and never falls back to plain `/mailbox`. Without keys the old plain mailbox is still used (until stage 7).
- `wake` = true for mood (not cleared), event / diary (not deleted), period (started/pain/better), chat, and never for `silent`, deleted, profile, unpair, story, like, comment, seen marks. It is the one thing about a message the server learns.
- Receiver: GET/WS -> decrypt -> apply -> remember the envelope id (last 1000, AsyncStorage) -> `POST /e2e/ack`. Not decryptable = ACKed and dropped. App error = no ACK (comes again). A failed ACK is harmless (duplicate by id). Cursor: `lastE2eSeq` in the partner store.
- Still plain in this stage (replaced in stage 6): video files (memories, stories, chat) and the old `Shared/<id>/` folder for items that already exist. Still image files no longer go to the server when E2E keys are confirmed (stage 4, below).

### Thumbnails and previews (stage 4; app side: `src/partner/media-*.ts`)
- A shared still image (event photo, memory photo, story photo, chat photo, sharp avatar) is NOT uploaded to `Shared/` any more when E2E keys are confirmed. Its reference stays the same shape (`Shared/<id>/<name>`, validated as before) but it is only a name now: nothing is on the server.
- Two ordinary encrypted queue messages carry the pictures: `{"t":"media","from","ts","silent":true,"ref":"Shared/<id>/<name>","kind":"thumb"|"preview","mime":"image/jpeg","w","h","data":"<base64 JPEG>"}`. `thumb` = 320 px, aim 10-30 KB (ladder down to 192 px / q 0.3). `preview` = 1080 px, aim 200-400 KB (ladder down to 720 px / q 0.4). `data` is at most 600000 characters (the queue takes 1 MB per blob; a 400 KB preview is about 540 KB as a blob). EXIF/GPS are gone (re-encoded). Never `wake` (no notification).
- Sender order: thumbnail first (a failure fails the share, so the caller's retry rules apply and nothing half-sent is reported), then the preview. Setting `sharePreviewWifiOnly` (default on): the preview is sent only on Wi-Fi/Ethernet; otherwise it waits in a private outbox (`meyou-partner-media/outbox/`, flushed whenever the encrypted listener starts: app start, push, foreground sync) and is dropped after 14 days. The thumbnail always goes at once.
- Receiver: decrypt -> `partner_media` row + file in the private `meyou-partner-media/` folder (database migration 16). Thumbnails stay for good (offline). Previews are a cache under `partnerCacheMb` (default 300 MB), least recently viewed evicted first; thumbnails are never evicted by the cap. A request for `preview` with only a thumbnail present shows the thumbnail. Items with nothing stored locally (old plain items, or a picture still on its way) fall back to the old server lookup.
- Privacy: files are in the app's private storage (not in the gallery or file manager, only the app can show them behind the app lock) and excluded from Android cloud backup and device transfer by `plugins/with-backup-exclude.js` (adds `files/meyou-partner-media/` to the SecureStore rules; never replaces them). Unpairing deletes the folder, the rows and the outbox. Settings > Media & cache: cache size, Wi-Fi-only switch, usage, "clear previews" (thumbnails stay).
- Not in this stage: the original file ("full quality", stage 6), video thumbnails and short video previews (need a native transcoder; stage 6 decides), hashes and deletion sync (stage 7).

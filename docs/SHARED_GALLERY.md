# Shared gallery (Direct vault -> "گالری مشترک" / "Shared gallery") — plan and stage log

**Goal.** The vault (Settings > partner area, Archive source) is renamed **Shared gallery** and becomes shared with the partner. The chat keeps its name **Direct**. The server keeps the current E2E queue and stores no files. Old vault files are NOT sent; only files added after stage 2 are. Archive and Explore were out of scope for stages 1-4; stage 5 adds the partner's side to them.

Stages 1-4 were planned up front, one per chat, cumulative zip; stage 5 was added afterwards by the owner's request.

| Stage | Content | Status |
|---|---|---|
| 1 | Rename (vault strings only) + fast add engine (no checksums, natural order, app-wide run, auto-resume) | **done** |
| 2 | Manifest + auto share on add (needs 2), legal texts (Privacy/Terms) updated to the real flow, picture sizes decided | **done** |
| 3 | Partner view: folders first, lazy tiles, concurrency limit, "full quality" on request (needs 3) | **done** |
| 4 | Preview limits (needs 4) + the two visible bugs: grey thumbnails, pixelated memory cover (needs 5) | **done** (grey cause not proven, see below) |
| 5 | The Shared gallery as a source of Archive and Explore: what this phone added (already the case: the vault) and what the partner added and this phone loaded or downloaded | **done** (phone not run) |

## Stage 1 result (what changed)
- **Rename:** every `vault*` string and `libSrcVault` (en + fa) now says "Shared gallery" / «گالری مشترک». The chat strings (`viewerSendDirect`, `directSent`, `directOpenChat`, `storyReply*`) are untouched. `privacyServerBody`, `privacyMediaBody`, `termsUseBody` still said "Direct files" (legal texts, changed in stage 2 with the real data flow).
- **Why the old add was slow:** `scan()` called `statOf` (`file.info({md5:true})`) for every file, i.e. hashed the whole 7 GB just to list it; `transferOne` hashed source and copy again, and in Move mode ran a JS SHA-256 over both files. Now: no MD5/SHA anywhere (`sizeOf`, `src/vault/files.ts`); the copy is checked by size only; Move deletes the original only when the copy has exactly the source's current size (`deleteVerdict`, source size unknown = original kept). The copy still comes first, so an interrupted move never loses a file.
- **Real move?** Not possible here: the source is shared storage / a document-provider folder and the vault is app-private storage (another volume), so Android cannot rename between them. Move = copy + verified delete (fast path above). Expect roughly the speed of a file-manager copy; not measured on a phone.
- **Not chosen:** indexing the picked folder in place (instant, no copy). The files would stay in the public gallery and the folder grant can be lost; the vault must stay private.
- **Order and structure:** `scan()` lists folders first, then files, names in natural order (`naturalCompare`: `IMG_2` before `IMG_10`, case-insensitive, total order); the copy queue follows that order, `VaultProvider.list` sorts with the same function. Folder structure is kept exactly; a name clash gets ` (2)`.
- **Background:** the transfer runs app-wide (leaving the add screen no longer pauses it); one job at a time (`busy` guard, later jobs wait in the journal and start after); `resumeOpenJobs` continues unfinished jobs 1.5 s after the app starts (`app/_layout.tsx`). **No foreground service** (removed in S10, `test-no-foreground-service`): if Android kills the app the transfer stops and resumes at the next launch. A job the person paused also resumes at the next launch ("Discard the rest" cancels it).
- **Add screen:** Copy is preselected and starts at once; Move asks once. The progress bar and counters are the existing ones, live while the transfer runs.
- Tests: `scripts/test-shared-add.mjs` (new, in the `pnpm test` chain), `scripts/test-vault.mjs` updated (size-only verdict, no checksum in the engine).

## Stage 2 result — manifest and auto share
**Why a manifest.** `shareFileResult` sends one file as thumb + preview + registration (+ a sync `add` event) = several queue messages per file; for thousands of files that floods the queue (1024 KB per blob, 256 MB per recipient, 30-day TTL). The existing sync layer also SHA-256 hashes every file (`registerForSync`), which is exactly the 7 GB read stage 1 removed, and keeps all ids in one JSON blob. So the gallery has its own small path; `sync_state` is untouched.

**Wire format** (`src/gallery/manifest.ts`, silent, never a notification, only from the encrypted queue):
```
{ t: 'gallery-manifest', from, ts, silent: true, n, z }
z = base64url(deflate(JSON { v: 1, e: [ { id, p: 'Trip/Day 1/IMG_0001.jpg', k: 'i'|'v'|'f', s: bytes, o: order } ], g: [ids removed] }))
```
- Up to 400 entries (or 64 000 raw chars, whichever first) per message: about 8-15 KB compressed. 30 000 files = about 75 messages. No picture, hash or outside path in it.
- `id` = `vault_items.id` (random UUID, stable when a file is hidden again). Folders are implied by the paths. `o` = the add queue's row id (`vault_queue` is AUTOINCREMENT, so it only grows, also across jobs): the partner lists files in the order the sender's file manager showed them; sub-folders sort naturally.
- Receiver (`applyGalleryManifest`): upsert by id in one transaction, so a repeated or reordered message changes nothing; a path taken by an older id goes to the new id; `g` removes ids and empty folders. A bad entry, wrong count, newer `v`, over-size or a zip bomb (inflate stops at 256 KB) makes the whole message ignored.
- **Dropped from my first plan, with reasons:** `job`/`seq`/`last` (nothing needs them: apply is idempotent and order-free, and a "job finished" flag can be lost if the app dies at the very end), and 300 entries / 200 KB (compression makes 400 entries tiny).

**Sender** (`src/gallery/gallery-db.ts`, `outbox.ts`, hook in `src/vault/import.ts`): every file copied from now on gets a row in `gallery_out` (migration 20) the moment it lands in the vault. The journal makes it crash-safe and offline-safe: the push (`flushGalleryManifest`, `manage.ts`) sends unsent rows in copy order and marks them sent only after the post worked. It runs for the first file, then every 50 files or 3 s (so the partner sees the first folder while the copy runs), when a job ends or pauses, and on every reconnect. Not paired or no keys = quiet, rows wait. Trash and Unhide mark the row gone (a file the partner never heard of needs no message); Restore and hide-again send it back in its old place. Old vault files are not in the journal and are never sent. Unpairing clears both sides (a new partner gets nothing of the old one).

**Receiver tables** (migration 20): `gallery_items` (id, path, parent, name, kind, size, ord; unique path), `gallery_folders`. `listGalleryPage(db, parent, offset, limit)` returns one page (folders first, then files by `o`) reading only that page's rows (`pageWindow`), and `galleryFolderCount` counts a subtree with an indexed range. Stage 3 builds the screen on these. `usePartnerStore().galleryTick` grows when the list changes.

**Picture sizes (owner's decision in the stage 2 chat; the numbers were finished in stage 4):** 256 px was too small. The small thumbnail ladder ends at 320 px (the 256/192 steps are gone, `LADDER.thumb`). The `preview` ladder IS the 500-700 KB picture (1600 px q .85 down to 1080 px q .6, `PREVIEW_MAX_BYTES` 700 000; there is no separate `tile` kind): it is what the viewer, the memory cover and an opened gallery file show. `MEDIA_MAX_DATA_CHARS` went from 600 000 to 960 000 so a 700 KB picture is accepted; sealed it is about 935 KB, under the 1 MB queue blob (tested with real encryption). Always sending the original was not chosen (a 6 MB photo per tile is too heavy over this queue; the original stays "Full quality", which now loads by itself when a photo is opened). Grid tiles stay on the light 320 px thumbnail.
- Tests: `scripts/test-gallery-manifest.mjs` (new, in `pnpm test`): format, limits, hostile input, zip bomb, copy order, 250-file paging, journal states, receiver store, size/queue fit, wiring. `test-partner`/`test-events` (migration list) and `test-e2e-media` (thumb ladder) updated.
- Also: `fflate` 0.8.3 added (`pnpm add`), Privacy/Terms strings (en + fa) describe the real flow.
- Not done on purpose: no screen shows the partner's list yet (stage 3); no notification for new files; no "told N of M" line on the add screen.

## Stage 3 result — partner view and lazy loading
**Screen.** `app/gallery.tsx` (opened from Settings > Shared gallery > "Open partner's gallery", shown when paired). Top level shows folders (and loose files); a tap on a folder pushes the same route with `folder` = its path, so Back works. Grid of 3 columns; sub-folders first (file-manager order), then files in the sender's copy order; a folder tile shows the number of files below it. Rows come from the manifest stored on this phone, 60 at a time (`listGalleryPage`, `onEndReached`), so a folder of 3000 files renders one page. `FolderLoader` (Explore/Archive) was NOT reused: it pages over storage providers (`StorageProvider.list`), while this list is already in SQLite with its own paging (`pageWindow`); the visibility/limiter idea was reused instead.

**Loading only what is on screen.** `FlatList` reports the visible tiles (`onViewableItemsChanged`, 30 % visible, 120 ms) -> `galleryWant(visible)` -> `createThumbScheduler` (`src/gallery/thumb-scheduler.ts`, pure, tested):
- at most **8 files asked at once**, in groups of up to 4 per message, in screen order (top first); a file whose picture is on the phone is never asked for;
- strictly the visible tiles, no look-ahead: a tile that scrolled away before its turn is dropped; files already asked stay asked (their answer is kept);
- no answer in 25 s = asked once more, then `failed` (grey tile; a tap retries at once, or it is tried again after 60 s when it is on screen again). A 3 s timer on the screen lets silent requests time out and the next ones go.
- Message `gallery-thumb-req` (partner -> owner, silent, <= 8 ids, `src/gallery/gallery-messages.ts`). The owner's phone answers with ONE ordinary `media` thumbnail per file (`kind: 'thumb'`, <= 30 KB, 320 px, re-encoded, `renderGalleryThumb`), one at a time, and answers nothing for a file that left the gallery (trashed/unhidden) or an old request (3 min, checked again while serving).
- **Naming:** a gallery file is `Shared/<item id>/<file name>` (`galleryRef`), the same scheme as every shared file, so the thumbnail cache (`partner_media`), the preview request and "Full quality" work unchanged. On the owner's phone `lookupSharedOriginal` / `sharedOriginalUri` fall back to the vault item with that id (`src/gallery/gallery-source.ts`, state `hidden` only).
- A tile redraws only when ITS picture arrived (`useGalleryThumbs.stamp[id]`, set from `onMedia`), not on every picture of the partner (the global media version would re-read the store for every tile on every arrival).

**Original only on request.** Tapping a tile that has its picture opens the existing `SharedViewer` (now with `hideDelete`, because "delete for both" belongs to the sync items, not to gallery files). "Full quality" / video download use the unchanged `orig-*` flow (40 MB photo, 1 GiB video, 4.5 MB windows, resumable). No hash exists for gallery files (stage 2 decision), so `verifyOriginal` returns "unknown" and the transfer is checked by size and the authenticated chunks only.

**Offline copy (owner's request, added after stage 3).** Everything of the gallery that reached the partner's phone stays there, so it shows while the owner's phone is off: the list (SQLite), every thumbnail (never evicted), and every preview/original/video that was loaded. These are **pinned**: `planEviction(rows, cap, pinned)` skips them, they do not count towards the cache cap (Settings > Media & cache), and "clear previews" spares them (`galleryPinned`, `media-store.ts`). Only unpairing removes them (and a file the owner removed from the gallery loses its pin: it is then ordinary cache). Cost: the pinned originals are not limited by any cap; a partner who opens many big photos keeps them all.

**Automatic original.** Opening a photo in the partner's gallery loads its original by itself (`SharedViewer autoOriginal`): once per opening, with the usual progress bar and cancel; a cancel or a failure (the owner's phone is off) leaves the "Full quality" button for a manual retry; an already stored original just shows. Videos stay manual ("Download", up to 1 GiB, resumable).

**Known limits (decided / to know):**
- The owner's phone must be **online** to answer anything NOT yet on the partner's phone: there is no server copy, so a tile stays grey while the other phone is off, and fills when it is back (tap to retry, or scroll away and back after a minute).
- Received thumbnails are kept for good (the existing rule: thumbnails are never evicted), about 10-30 KB each; a partner who scrolls through 30 000 files would keep up to ~600 MB. Only tiles that were on screen are fetched, so a 7 GB gallery of a few thousand files is ~50-100 MB. A cap with LRU for gallery thumbnails is not built.
- A non-media file (`k: 'f'`) shows as a file tile and cannot be opened in this stage. Folder tiles have no cover picture yet.
- The grid uses the 320 px thumbnail; the viewer shows it, then the 500-700 KB preview (asked for when only the thumbnail is there), then the original (automatic for photos).
- Tests: `scripts/test-gallery-view.mjs` (new, in `pnpm test`): request message and limits, ref round-trip and the `media` answer, scheduler (order, 8-at-once with 3000 files, scroll skipping, timeouts/retries, failed posts, a 600-tile scroll with no double ask), paging of a 3000-file folder, wiring.

## Stage 4 result — preview limits and the two visible bugs
- **Preview limits removed.** The "previews on Wi-Fi only" setting is gone (`sharePreviewWifiOnly` in `settings-store.ts`, its switch in Media & cache, the `unmetered`/`wifiOnly` checks in `media-send.ts`, `askPreview` and `manage.ts`). A preview goes on any network, at once after the thumbnail; if that post fails it waits in the outbox. It is still asked for by the partner's screen when only the thumbnail is there (`orig-preview-req`). **Gallery files never send a preview ahead of time** (a thumbnail only on request, then the preview when the file is opened), so a 7 GB gallery pays nothing for previews it never shows; no separate "tile" kind exists.
- **Pixelated memory cover.** `HERO_THUMB = 1280` (`src/media/thumb-cache.ts`) is asked for by the memory card cover (`DiaryCard.tsx`) and the picture at the top of a memory (`app/diary/[id].tsx`); `thumbEdge` now has a third size (320 / 640 / 1280, `THUMB_EDGES`). A shared (partner) picture at full width uses the 500-700 KB preview.
- **Grey thumbnails.** Every swallowed failure now writes one line to Settings > Diagnostics (`src/diagnostics/thumb-trace.ts`): `thumb <step> [<extension>] <Error>: <message>` with steps `exists`, `decode`, `video-frame`, `resize`, `save`, `copy`, `cache`, `provider`, `display`, `image-error`, `job`; the same failure is written 3 times, then at counts 10, 100, 1000; the first 5 successes are logged too (`thumb ok`). Used in `ensureThumb` (`thumbs.ts`), `loadThumb` (`thumb-cache.ts`) and the tiles' `onError` (`Thumb.tsx`, `GalleryTile.tsx`). **The cause itself is NOT found:** it needs the log of a real phone, which this sandbox does not have. Read the lines after opening a grid: `decode`/`video-frame` = the file or codec, `save`/`copy` = storage, `display` or `image-error` = the picture was made but cannot be shown, `provider` = no thumbnail from the source. Send those lines for the fix.
- Tests: `test-e2e-media` (preview ladder 1080-1600 px, 700 KB limit, no network condition), `test-gallery-manifest` (sizes fit the queue blob), `test-vault` (`thumbEdge` 320/640/1280).

## Stage 5 result — the Shared gallery in Archive and Explore
**Owner's rule:** whatever media goes into the Shared gallery (added here, or sent by the partner and loaded/downloaded here) shows in Archive and Explore.
- **Own side needed nothing:** the vault was already the one Archive/Explore source and the add engine already rebuilds the index (`build(true)` in `vault-add.tsx`). Only the partner's side was missing.
- **New source, kind `partner`, id `partner-gallery`** (`src/storage/partner-gallery-provider.ts`, read only, built in, registered next to the vault; sources store v7 adds it to saved lists). Archive/Explore mode `vault` now means the kinds `vault` + `partner` (`sourceKindsOf`, `applySourceMode`, `FolderPage`). Nothing else of the Archive/Explore/viewer/search/tags/albums code was rewritten: they already work on providers.
- **What it lists (decision):** only gallery files of which this phone holds a picture (thumbnail, preview or original in `partner_media`), found with one indexed range read + the manifest rows of those ids (`loadedGalleryItems`, `src/gallery/gallery-db.ts`). The partner's other files (never scrolled to, never loaded) stay only in the partner's gallery screen: listing all would put thousands of grey tiles in Explore. Changing this is one predicate in `loadedGalleryItems`. Non-media files (`k: 'f'`) are never listed. Listing never asks the partner's phone for anything.
- **Shape in Archive:** one folder at the top, named like the partner's gallery screen (`galleryPartnerTitle`), holding the partner's folder tree (only folders with a loaded file below). Explore and search see the files flat. Folder/file ids: `pgd:<folder path>` / `pg:<item id>`.
- **Pictures:** tiles use the 320 px thumbnail; a tile asking for more than 400 px (Explore's large ones) gets the 500-700 KB preview when stored; the viewer shows original > preview > thumbnail. `partnerOriginalUri` (`media-store.ts`) is the exact-original lookup.
- **Viewer:** a file that exists only on the partner side and has no original here gets the same "Full quality" / "Download video" button as the partner's gallery screen (`components/gallery/ArchiveOriginalBar.tsx`, the existing `requestPartnerOriginal`; needs the partner's phone online). When the original arrives the page loads again and a video can play. A file that also exists in the vault shows no button.
- **Date and identity:** the manifest has no file date, so a partner file's date is when its thumbnail reached this phone (a file with no thumbnail, e.g. a downloaded video without a poster, has no date). Identity (favourites, tags, albums) is name+size+that date, stable because the thumbnail row is never rewritten.
- **Staying current:** the library-index signature now contains `partnerEpoch()` (media version + gallery tick), so a plain `build()` lists again only when the partner side changed; `startArchiveSync` (`archive-sync.ts`, started in `app/_layout.tsx`) calls it 6 s after the last change, only if an index exists. Explore keeps its mix until the next pull (existing rule); Archive grids reload with the signature.
- **Read only:** no delete/trash/tag-by-copy for partner files (`canDelete: false`; the trash button works on vault refs only). The storage analyzer skips partner-only files (not stored here at that size). Unpairing clears the list and pictures, so the source becomes empty by itself.
- **No data-flow change:** nothing new is sent or stored, so Privacy/Terms are unchanged. No migration, no server change.
- Tests: `scripts/test-gallery-archive.mjs` (new, in `pnpm test`): ids, tree/paging/stat, dates, the SQL loader on a real SQLite (gallery vs chat refs, 1000 files over the 400-id chunk), partner-only rule, mode/sort/analyzer, wiring. `test-vault` updated (`sourceKindsOf`, sources v7). Run here with stand-ins for the packages this sandbox lacks; typecheck, the full `pnpm test` chain, the Android export and a phone were NOT run.

## Risks
- Size-only verification cannot detect a bit-flip in a copy. Accepted by decision (speed); the original is deleted only when sizes match and the copy call did not throw.
- 7 GB of copies doubles the used storage in Copy mode; Move frees it file by file (the space check for Move only needs the largest file).
- Android may kill the app during a long transfer (no foreground service). Mitigated by the journal and auto-resume; not by a background service.
- Manifest batches must be idempotent and order-independent (queue delivery can repeat).
- Phone checks are NOT run (see HANDOFF): the copy speed, the SAF `File.size` on every document provider, and auto-resume after a kill need a real phone.

Legend: `[ ]` not started · `[x]` done. Item codes: B bug · A addition · C change (N notifications, M mood, E events, D diary/archive, H home, S settings).
Rules for every phase: the HARD RULE of `PROMPTS.md` (no invention, search for an existing tool first), extend finished code, every string in fa + en (parity), UTC Gregorian dates, run typecheck + tests, update HANDOFF, give `meyou-src.zip`. One phase per chat.

## Findings that shape the plan
1. **Most sync bugs are missing protocol fields, not delivery bugs.** `EventMessage` has no `icon`, no note ("what is going to happen?"), no photo; `Profile` has no `togetherSince` (it lives only in the local partner store); `MoodMessage` cannot say "cleared". The diary is local-only by design (also stated in `docs/SERVER_QA.md` and the Privacy text): sharing it is a **new feature**, not a fix. Affected: M-B1, E-B2, E-B3, H-B1, D-B1.
2. **Notification channel:** the app and the server use channel `meyou-partner` with importance DEFAULT (no pop-up). Android never changes an existing channel's importance, so the fix needs a **new channel id** (e.g. `meyou-partner-v2`, importance HIGH, sound default) on both sides, plus FCM `android.priority: high` and `notification.sound: default` from the server.
3. **Server pushes know only `mood` and `event`** (columns `notify_mood`, `notify_event`). New shared things (diary, period) need new types and opt-out columns. Do all server work **once, in R1a**, so only R1a needs `sudo ./setup.sh update`; every other phase needs only a new APK.
4. **Attachments** (event photo, diary media) must not go through the mailbox (32 KB limit). Plan: the sender uploads them with the existing S5 upload into a library folder `Shared/<id>/`; the message carries the server path; the partner reads them with the media API (one household, both devices already have access).
5. Closed-app push (N-B3) was seen on a cloned app; R1b first checks it with the server log and `push-test` before changing code.

- **Result:** *Research:* no maintained npm library fits (the few packages are tiny, unmaintained, and one is a paid API wrapper); every tracker and calculator documents the same arithmetic, so it is ~100 lines of plain date maths and no engine: cycle = first day to first day; prediction = average of the last 6 plausible cycles (default 28, gaps outside 15–60 days are ignored as typos/missed logs); next period = last start + average; ovulation = next period − 14 (luteal); fertile window = 5 days before through 1 day after; PMS = last 5 days before the next period; period length fixed at 5 days; "irregular" = spread > 7 days or average < 21 / > 35 (Maven Clinic rule). Phase names: `period, follicular, fertile, ovulation, luteal, pms, late` (`late` = predicted date passed, nothing logged). *Code:* `src/period/cycle.ts` (pure: `predict`, `phaseForDay`, `cycleStats`, ...), `src/period/period-db.ts` (table `period_events`, `logPeriodLocal`, `applyPeriodMessage`, `listPeriodEvents`, `predictNext`, `dayInfo`, `deletePeriodEvent`, `buildPeriodMessage`), migration 9 `r5a-period` in `database.ts` (one row per owner/kind/day; `from_me` keeps my log and the partner's apart). *Messages:* `period` `{ kind: started|pain|better, date }` already existed in the parser (R1b); `date` = the day (midnight UTC), never later than the send day.

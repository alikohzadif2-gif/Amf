# meYou — Server Plan · `docs/SERVER_PHASES.md`

> Living instruction file for the **server track** (phases **S1…S12**). Same working method as `docs/UI_PHASES.md`:
> one phase per chat, tick it, log it, return the updated source zip. The UI track (U1–U27) is finished and stays as history.
> Goal of the track: connect the app to the user's own VPS and switch on, one by one, **(1) connection, (2) media backup and browsing, (3) partner, (4) push notifications through Google FCM** (no permanent notification, no ntfy).

## 2. Rules for every phase

1. **One phase per chat.** If the chat is nearly full: stop at a clean point, log it as `PARTIAL` (done / left / exact next step), do not tick, deliver the zip.
2. **Server code lives only in `server/meyou-server/`** (own `package.json`, own lockfile, own tests). The root `pnpm-workspace.yaml` must not include it. The root `tsconfig.json` must **exclude** it (`"exclude": ["server/meyou-server","node_modules"]`) so `pnpm typecheck` of the app is unaffected. Do not add server-only packages to the app's `package.json`.
3. **No secrets in the repo, ever.** `.env`, service-account JSON, tokens, `google-services.json` are git-ignored; only `.env.example` and docs are committed. Tokens in logs are forbidden.
4. **The API is the contract.** Any change goes into `docs/API_CONTRACT.md` (new section D = household/auth/mailbox/push) and into HANDOFF "Contract changes" in the same phase. Never silently diverge.
5. **Stay Android-only, local-first.** The app must keep working with no server configured (flags off or no server saved). Every network feature keeps a Mock/Fake implementation for tests.
6. **Persian is mandatory** for every new app string (fa + en, `pnpm test:i18n`), RTL-safe layout (`rowOf`/`alignOf`, logical margins). Server messages shown to the user are keys, not hard-coded text.
7. **Reuse before writing.** Use maintained libraries for: HTTP framework, rate limiting, image resize, ffmpeg wrapper, FCM (`firebase-admin`), QR. Glue code stays thin. Web-search the official docs before using an API from memory (Fastify, firebase-admin, expo-notifications, sharp).
8. **Security baseline** applies to every server phase: tokens random (≥ 32 bytes) and stored only as SHA-256 hashes, constant-time comparison, rate limit on auth and join endpoints, request size limits, path-traversal-safe file access (resolve + prefix check), no delete endpoint for media, CORS off, `trustProxy` only for Caddy.
9. **Checks.** Server phases: `npm test`/`pnpm test` inside `server/meyou-server/` plus `docker build` if Docker exists in the sandbox (otherwise say it was not run). App phases: root `pnpm typecheck`, `pnpm test`, `npx expo export --platform android --max-workers 1 --no-bytecode`; and `CI=1 npx expo prebuild --platform android --no-install` when native config changed (then delete the generated `android/`). Say plainly what could not be run.
10. **End of phase:** tick · log (section 7) · HANDOFF Status (3–5 lines) · QA lines added to `docs/SERVER_QA.md` · export zip with the procedure in HANDOFF (also exclude `.env*`, `android/`, `server/meyou-server/node_modules`, `server/meyou-server/data`).

## 3. Decisions

### 3.1 Locked (from the user)
- Own VPS with a **domain**. HTTPS through **Caddy** (automatic certificates).
- **No permanent notification**, so partner delivery is **push via Google FCM**. ntfy and the foreground service (`react-native-notify-kit`) leave the project (removal in S10/S11).
- The old brief rule "NO INVENTING" is **dropped**: a thin own server is allowed, built on maintained libraries.
- Order: connection first, then media, partner, notifications.
- One couple per server (two devices).
- Android-only. Persian kept.

### 3.2 Defaults (change here before the phase starts if you disagree)
| # | Topic | Default |
|---|---|---|
| Q1 | Push text | **Generic, no message content** (e.g. "New status from your partner"), localized to the receiver's app language (the app sends `lang` with its FCM token). Content is never sent through Google. |
| Q2 | Push type | FCM **notification + data** message, Android channel `meyou-partner`, high priority, TTL 24 h. No headless background task. Tapping it opens the app and syncs the mailbox. `profile` and `unpair` messages are data-only (silent). |
| Q3 | Mailbox retention | 30 days or 1000 messages per household, whichever is smaller. The client de-duplicates by `seq`. |
| Q4 | Invite code | 24 random chars, single use, expires in 30 minutes, rate limited. |
| Q5 | Media roots | Each folder directly under `$DATA_DIR/library/` is a root. Created at init: `Photos`, `Videos`. Others appear when a folder is created. |
| Q6 | Server stack | Node.js 22 LTS, TypeScript, **Fastify**, built-in `node:sqlite`, `sharp` (image thumbs), `ffmpeg` (video posters, in the Docker image), `firebase-admin`, `ws` via `@fastify/websocket`. Tests with `node:test`. |
| Q7 | HEIC | Best effort (ffmpeg fallback). JPEG/PNG/WebP/MP4/MOV/WebM are the supported formats. |
| Q8 | Backup default | Wi-Fi only, charging not required, skips files already on the server (hash/size/name match). Never deletes on the server or on the phone. |
| Q9 | Ping | `GET /api/v1/ping` is **public** and returns only `{ name, version, features[] }`; everything else needs `Authorization: Bearer`. |
| Q10 | Server language | English logs; user-facing strings only inside the app. |

## 4. Architecture and API (what the phases build)

```
phone A ─┐                          ┌─ /data/library/…  (originals)
         ├─ HTTPS ─ Caddy ─ meyou-server ─ SQLite (/data/db) + cache (/data/cache)
phone B ─┘   (WS for live)          └─ FCM HTTP v1 (push wake-ups) ─▶ Google ─▶ phones
```

**Model:** one household, max 2 devices. Device = `{ id, name, role: owner|member, tokenHash, createdAt, lastSeen, fcmToken?, lang? }`.

**Existing contract kept (A + C):** `/ping`, `/roots`, `/tree`, `/items/{id}/thumb|preview|file` (Range), `/changes`, resumable `/uploads`. These are implemented by the server in S3/S5 exactly as in `docs/API_CONTRACT.md`.

**New (section D, written into API_CONTRACT.md by S1/S7/S9):**
- Bootstrap (server CLI, not HTTP): `meyou-server init` creates the household and the owner device, prints a **link** `meyou://server?url=<…>&token=<…>&name=<…>` and a QR (ASCII) plus JSON (same payload as Contract C.6).
- `GET /api/v1/me` → `{ deviceId, role, household: { partner: { deviceId, name } | null }, features }`.
- `POST /api/v1/invites` (owner) → `{ code, expiresAt, link }` with link `meyou://join?url=<…>&code=<…>`.
- `POST /api/v1/join { code, deviceName }` (public, rate limited) → `{ deviceId, token }`; consumes the invite; fails when 2 devices already exist.
- `DELETE /api/v1/devices/{id}` (owner, or the device itself) → revokes the token (this is how "unpair" works).
- `POST /api/v1/mailbox` body = the existing partner message JSON (`t: mood|event|profile|unpair`, `from`, `ts`, …, ≤ 32 KB) → `{ seq, time }`. Delivered to the **other** device only.
- `GET /api/v1/mailbox?since=<seq>&limit=100` → `{ messages: [{ seq, time, body }], cursor }`.
- `GET /api/v1/mailbox/ws?since=<seq>` WebSocket (token in the header, never in the URL) pushes new messages while the app is open.
- `PUT /api/v1/push/token { fcmToken, lang }` and `DELETE /api/v1/push/token`.
- `features` in `/ping`: any of `media`, `mailbox`, `push` — the app switches a module on only when the server announces it.

**App touchpoints (existing code):** `src/server/{client,server-provider,upload,token-store,qr,test-connection}.ts`, `src/settings/sections/ServerConnectionSection.tsx` and the `app/settings/` server screens, `src/partner/{manage,ntfy-client,pairing,messages,background-service}.ts`, `components/home/ConnectCard.tsx`, `app/_layout.tsx` (`PartnerListener`), `src/constants/features.ts`, `scripts/fake-server.mjs`, `scripts/fake-ntfy.mjs`.
